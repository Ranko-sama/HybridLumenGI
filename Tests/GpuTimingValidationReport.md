# GPU timing feedback source validation

Run with `powershell -NoProfile -ExecutionPolicy Bypass -File Tests/Validate-GpuTiming.ps1`.

The harness compiles the actual `Runtime/HybridLumenGIGpuTiming.cs` with .NET 8 through `Invoke-CSharpHarness.ps1`. Unity's sampler, recorder, capability property and command-buffer APIs are recording substitutes. This checks C# control flow and state contracts; **it does not execute Unity, a native profiler, GPU timestamps, DX12 drivers, Editor rendering, or a Development/Release Player**.

Result on 2026-10-27: **9,583 assertions passed in 15 scenarios**, using Windows PowerShell 5.1 and PowerShell 7. Runtime source SHA-256: `C895D10DAA0995B68672D1989D7FDABEF5C76B6F86ABAD0C4A098214B3C8C7ED`. Unified candidate validation is a separate gate.

The scenarios cover eight completed consecutive submissions before accepting feedback; three required scopes and their sum; native/raster command pairing; duplicate camera renders and scope calls; capability loss/recovery; missing or invalid samplers; missing, repeated, nonpositive and changing GPU samples; recorder exceptions; generation changes; skipped and backwards frames; stale/foreign callbacks; invalidation/disposal while a marker is open; history-ring wrap; and 1,000 camera-state replacements against the native-marker name cap.

## Implemented contract

- A camera instance requests one of **32 lifetime channels** only when timing is enabled and GPU recorder capability is present. Each channel has at most seven fixed names: ReceiverCapture, Transport, Composite, IdentityClear, IdentityMask, IdentityCapture and IdentityResolve. Only required names are created/enabled; failure to create an optional marker does not disable subsequent baseline mode. Names use the bounded channel index, with at most **224 distinct native marker names**, including Editor domain reloads.
- Channels are not recycled during a managed domain lifetime. `Dispose` disables recorders. Exhaustion reports `ChannelLimitReached`, yields no measurement and emits no new timing scopes. Rendering and static work budgets can continue. This is a deliberate remaining production limitation for long sessions with camera-state churn, not a completed channel-reuse solution.
- Each frame token binds its required scope mask: 7 for baseline or 127 for identity mode. All three or seven scopes must actually end, each locally within its own pass. Mode changes clear history before any old observation can be read; eight consecutive completed submissions with the same generation and mask are required. Polling requires the expected `frame - 3` entry and exactly one block before and after each elapsed-time read. Core scope durations must be positive. Individual identity scopes may be zero, but all four must have valid blocks and their sum must be positive; an entirely zero identity chain is unavailable feedback.
- Duplicate renders, missing scopes, frame gaps, configuration/backend generation changes and explicit invalidation reject the affected history. Already opened markers can still be ended after invalidation or disposal. Callers must put `RecordEnd`/`EndSample` in a `finally` block.
- A second camera render in the same engine frame invalidates the history and cannot consume a second result. The first call cannot predict that later render: a caller that already acted on its returned measurement must reset its bounded controller when the duplicate is discovered.
- No CPU elapsed value substitutes for missing GPU timing. Negative, absent or ambiguous values, zero core durations and an entirely zero identity chain are unavailable feedback. Optional per-pass zero durations are accepted only within the complete positive identity chain described above.
- `RejectCommandRecording()` permanently stops feedback from this instance's channel after an actual marker-command failure. Re-enabling, changing scope masks or generations, and ordinary invalidation cannot rehabilitate a marker whose native recording outcome is unknown. Existing opened tokens may still close their CPU bookkeeping; the channel is never recycled. This affects optional feedback, not GI rendering or static work caps.

## Native API evidence and limits

UnityCsReference was inspected at commit [`1c2d7db69c060103b6dc087af725442d1efaef9c`](https://github.com/Unity-Technologies/UnityCsReference/commit/1c2d7db69c060103b6dc087af725442d1efaef9c), Unity 6000.0.85f1. SRP Core 17.0.4 was inspected at Graphics commit [`feb4de2d9a93a4ae10d287d3a6d7003d08ea3e53`](https://github.com/Unity-Technologies/Graphics/commit/feb4de2d9a93a4ae10d287d3a6d7003d08ea3e53).

- [`CustomSampler.Create`](https://github.com/Unity-Technologies/UnityCsReference/blob/1c2d7db69c060103b6dc087af725442d1efaef9c/Runtime/Profiler/ScriptBindings/Sampler.bindings.cs#L90) sets `AvailabilityNonDevelopment` and optionally `SampleGPU`. Immediate `CustomSampler.Begin/End` are conditional on `ENABLE_PROFILER`.
- [`CommandBuffer.BeginSample(CustomSampler)` and `EndSample(CustomSampler)`](https://github.com/Unity-Technologies/UnityCsReference/blob/1c2d7db69c060103b6dc087af725442d1efaef9c/Runtime/Export/Graphics/RenderingCommandBuffer.bindings.cs#L939) are not conditional in the managed source. [`RasterCommandBuffer`](https://github.com/Unity-Technologies/Graphics/blob/feb4de2d9a93a4ae10d287d3a6d7003d08ea3e53/Packages/com.unity.render-pipelines.core/Runtime/CommandBuffers/RasterCommandBuffer.cs#L219) forwards both CustomSampler overloads. In contrast, [`ProfilingScope`](https://github.com/Unity-Technologies/Graphics/blob/feb4de2d9a93a4ae10d287d3a6d7003d08ea3e53/Packages/com.unity.render-pipelines.core/Runtime/Debugging/ProfilingScope.cs#L230) has empty non-Development Player constructors and disposal.
- [`Recorder`](https://github.com/Unity-Technologies/UnityCsReference/blob/1c2d7db69c060103b6dc087af725442d1efaef9c/Runtime/Profiler/ScriptBindings/Recorder.bindings.cs#L20) wraps shared, capacity-one `ProfilerRecorder` instances with per-frame sums. Its `isValid` checks the CPU recorder handle; GPU values can still be absent. Its thread filtering affects only its CPU recorder. The wrapper does not use that filter to claim camera isolation.
- Unity documents a **three-frame delay** for [`gpuElapsedNanoseconds`](https://docs.unity3d.com/cn/6000.0/ScriptReference/Profiling.Recorder-gpuElapsedNanoseconds.html) and [`gpuSampleBlockCount`](https://docs.unity3d.com/cn/6000.0/ScriptReference/Profiling.Recorder-gpuSampleBlockCount.html). The latter describes complete or running blocks; it is not a completion-fence API.
- [`ProfilerRecorderSample`](https://github.com/Unity-Technologies/UnityCsReference/blob/1c2d7db69c060103b6dc087af725442d1efaef9c/Runtime/Profiler/ScriptBindings/ProfilerRecorder.bindings.cs#L121) exposes value/count only. No GPU query ID, frame ID or native completion receipt is supplied. `LastExpectedSourceFrame` therefore means the documented-delay assumption, not verified query identity. Reading count before and after elapsed catches some changes but cannot make the properties atomic.
- The [`Recorder` documentation](https://docs.unity3d.com/cn/6000.0/ScriptReference/Profiling.Recorder.html) says collection does not depend on the Profiler being enabled, but retains an Editor/Development-only statement. The newer managed flags above and [`ProfilerRecorder` documentation](https://docs.unity3d.com/ja/6000.0/ScriptReference/Unity.Profiling.ProfilerRecorder.html), which includes Release Players, are broader. The implementation therefore probes capability and actual samples instead of claiming universal Release GPU timing support. Native platform behavior remains an unexecuted validation requirement.

This Recorder fallback provides delayed heuristic feedback for a controller with absolute work caps and cooldown. It is not a hard real-time guarantee, and its lifetime channels remain non-recyclable. The optional [native DX12 backend](../Documentation/NativeGpuTiming.md) instead uses submission IDs and completion fences to recycle query slots; its separate [validation report](NativeGpuTimingValidationReport.md) distinguishes CPU, mock-host WARP and still-missing Unity/physical-GPU evidence. This Recorder harness does not validate that backend.
