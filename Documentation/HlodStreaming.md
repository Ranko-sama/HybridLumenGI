# HLOD publication and additive scene IO

These modules separate scene loading, GPU preparation and publication. A completed `LoadSceneAsync` operation means Unity has activated a scene. It does not mean that its SDF, material cards or lighting cache are ready.

## Atomic HLOD transactions

The scene table uses three states in `ProxyGpuData.identity.w`:

| Value | State | World visibility |
| --- | --- | --- |
| 0 | Absent or waiting for geometry upload | Not traced |
| 1 | Published | Included in the scene BVH and live backends |
| 2 | Warming | Available to SDF/material/cache preparation; excluded from live world tracing |

The topmost authored HLOD parent represents the far state. Descendant leaf proxies form the near state; intermediate aggregates are not simultaneously published. The complete old published set is retained while slots are reserved and the target set uploads under the existing geometry budget. The target's entire staging set must fit alongside the old representation. If it does not, `PendingCapacity` reports blocked groups and the old representation stays active. Increasing the capacity causes resource reallocation and therefore requires normal full initialization.

If a published member becomes unavailable or leaves its authored group, Scene withdraws the invalid set before reserving slots. A reparented detail can warm in the destination group while the old root is still waiting. An unchanged member returned to warming leaves world traversal and needs a fresh lighting receipt before publication.

An already published set can stay live through a pose change when every revised member uploads in that preparation. If the existing upload allowance leaves a member absent, Scene withdraws the entire set before it updates the scene buffer and BVH. Members of the current target can finish warming and need fresh readiness receipts before the whole set returns. The withdrawal invalidates the previous bounds of the entire set. [Controlled geometry revision](../LocalComparison/Review/partial-hlod-upload-163/result.md)

A streamed binding instance or generation change also invalidates the old publication, even if a camera missed the intervening detachment. The new generation warms under the normal geometry, material and lighting receipts. The default independent exporter uses each eligible Base camera's previous complete publication for ordinary rendering at cull. The camera must be within the far boundary of the closest eligible root or detail. Binding identity and current membership qualify the set. A pose or material revision on an unchanged binding can preserve the ordinary draw while GI prepares its updated data. [First cull across the far boundary](../LocalComparison/Review/streamed-hlod-cull-range-202/result.md)

For independently streamed asset pages, enabled representation bindings declare the authored group before their meshes arrive. A partially bound detail set waits while a valid published root continues to contribute. If the root has no bound mesh yet, Scene uses the root binding's authored world bounds for distance and hysteresis. A complete near set can start preparation and publish after its ordinary readiness receipts. A root that has never been enabled reports a `rootStableId` of zero, and callers can query the group with the root Proxy reference. [CPU regression and release scope](../LocalComparison/Review/streamed-hlod-membership-145/release-notes.md)

Managed automatic page demand follows the same root and leaf roles in a nested tree. An intermediate binding can declare the authoring hierarchy while yielding residency to selectable members. Previously bound pages retire through the existing consumer and completion checks. [Asset-page demand contract](IndependentAssetPages.md)

The unified sample follows the same rule. It enables all authored detail proxies together once their own pages are bound and the enabled root binding still declares the group. The root may still be waiting for pages. The group becomes eligible for ordinary drawing after the complete publication check. If current preparation has no complete publication, the sample hides the whole set at the camera boundary, including when the underlying binding generations have stayed the same. [Cold detail admission](../LocalComparison/Review/cold-detail-admission-154/result.md) · [Same-binding withdrawal and recovery](../LocalComparison/Review/withdrawn-sample-raster-184/result.md)

A terminal error on a resident streamed binding withdraws its destination and proxy from new readers, even while its last request still wants the pages. The unavailable-binding path detaches the current generation and holds its page leases through the existing completion gate. An enabled binding with a live Proxy continues to declare its authored role, whether it fails before or after binding. Once a required detail reaches terminal failure, Scene excludes the source, withdraws any invalid publication and can stage the complete authored root when available. An unbound terminal failure can use this fallback on first entry. A healthy leaf still loading keeps a partial near set waiting. The root publishes only after its normal readiness receipts. When no complete set qualifies, the group stays hidden. Disabling a binding or changing its parent updates the authored set on the next preparation. [Controlled retirement sequence](../LocalComparison/Review/failed-streamed-destination-194/result.md) · [Resident detail failure](../LocalComparison/Review/failed-detail-membership-264/result.md) · [Terminal failure before binding](../LocalComparison/Review/failed-unbound-detail-268/result.md)

At near-field cold start, a group uses its existing authored root when the declared detail set exceeds the normalized total scene-slot capacity. Enabled leaf bindings count while their pages are pending. A currently published root can stay in this fallback until the declared set fits. The root warms under the upload budget and requires complete geometry, material and lighting receipts before publication. `PendingCapacity` counts one blocked group. When the full detail set binds and fits beside the root, the normal transaction stages and publishes it. Material-card capacity, temporary slot competition and native rendered coverage have separate acceptance conditions. [Fully bound set](ReviewBrief-HlodColdStartRootFallback01.md) · [Partially bound set](../LocalComparison/Review/hlod-incomplete-capacity-240/result.md)

At near-field cold start, when the declared healthy leaves need every scene slot, Scene waits for the full detail set even if the root binds first. The complete set can then stage under the original upload allowance and publish after every matching readiness receipt. This can delay the first visible representation until the leaves arrive. An already published root uses the coexistence rule above. [Root-first exact-capacity comparison](../LocalComparison/Review/hlod-root-first-capacity-275/result.md)

The owner calls `ReportReadiness(stableId, revision, geometryReady, materialReady, lightingReady)` for each prepared proxy. Reports are accepted only for a currently resident matching identity/revision. Once every target member has a matching complete report, the next `Prepare` publishes the entire target set and removes the old set in the same update. `InvalidateReadiness()` must be called when cache/backend/atlas generations change; callers must reject stale GPU completion reports before forwarding them. The readiness container itself is a CPU receipt table, not a GPU fence.

The renderer integration uses `HybridLumenGIHlodReadback` after recording irradiance updates. Its snapshot contains the actual variable card index set and generations, owner layout generation, material atlas generation, cache epoch/grid and geometry source. The callback rechecks current source eligibility and identity, and rejects changed SDF assets, textures/content versions, bounds or transforms even if a replacement upload has already become ready. Normal double-buffered cache alternation is allowed; cache reallocation requires epoch advancement or explicit invalidation. Source guards run again before scene publication.

One readback covers the byte range from the first to the last card in the warming snapshots. The callback maps the local array back to physical card indices. The four-work-frame request interval and single pending request bound apply. A complete return can provide empty patch evidence for the matching cards. Scattered card indices can span the full cache. [Requested bytes and scope](../LocalComparison/Review/hlod-readback-span-276/result.md)

For a baked-chart owner, **every required chart** needs at least one genuinely covered patch, and every covered patch must meet the initialization accumulation threshold, currently two by default. Explicitly empty patch cells are allowed, but an entirely empty required chart blocks publication. Tiny charts and alpha-clipped material with no surviving texels can therefore remain warming. An owner without a chart asset uses the approximate six-view fallback and requires only object-level nonempty coverage. Neither gate measures complete geometric coverage or irradiance convergence, and uniform material fallback never counts as a covered chart.

When a replacement stays warming, log runtime diagnostics or press **F2** in the unified sample. Look for `lastHlodCoverageBlock` in the camera diagnostics (`cameraGi` in the sample ledger). If `observed` is true, the existing readback found a blocker at `sourceWorkFrame` for the named owner and revision. For baked charts, `cardOrdinal` is the zero-based chart index in the owner's asset. `physicalCard` is its pool index at that frame. The local `patch` index addresses the grid within that card. A value of −1 means the reason applies to the whole card or owner.

“Required chart has no covered cache patch” means every cell in that chart was read and explicitly empty. Check the chart's projected size and material alpha coverage. “Covered patch below required sample age” means the GPU returned a matching patch that still needs initialization. An invalid entry or mismatched tag has its own description, as does a missing entry in a truncated read. An empty six-view fallback is reported at owner level. The field describes the first blocker observed in that callback. When `observed` is false, consult the existing warming, pending and readiness fields. Coverage at capture time does not measure the irradiance's convergence or an object's covered surface area.

The material cache admits complete variable chart sets, prioritizing published owners before warming owners. A configured invalid/stale asset, unsupported chart material or a set larger than available capacity is rejected as a whole. It is not silently converted to six views or partially declared ready. Both old and target scene representations and their required material pages need sufficient staging capacity. Changing the patch grid rebuilds material/anchor storage and invalidates pending initialization results. See [SurfaceCache.md](SurfaceCache.md) for card mapping and allocation.

If ordinary admission would remove a current published group's cards, the cache retains the group only when all members still have matching layouts and current ready sources. Already selected matching layouts of other owners stay in place. New allocations compete for the remaining tiles under the original order, and the group gives up its cards when it leaves the prepared scene. [Fixed-capacity handoff in the DX12 Editor](../LocalComparison/Review/published-hlod-card-retention-185/result.md)

For a camera already using DXR and a positive shared RTAS build quota, a ready replacement that needs a build waits with the old group still published if the quota is exhausted or another camera is first in the queue. An eligible exact target can require a build when a live exact member leaves or when a new exact member fits alongside the retained triangles. Removing an exact member can also require a build when an eligible ordinary exact object is guaranteed to remain selected alongside the replacement. The camera joins the existing age-ordered queue after recording DXR with the old group. A subsequent build checks the queue again and pays its actual work under the existing limits. Withdrawal of the ready replacement clears its waiting demand. [Build count and cancellation in DX12](../LocalComparison/Review/hlod-rtas-turn-187/result.md) · [Earlier queued demand](../LocalComparison/Review/hlod-rtas-older-197/result.md) · [Exact details to an approximate root in DX12](../LocalComparison/Review/hlod-exact-departure-281/result.md)

`IsPublished(slot)`, `IsWarming(slot)`, `PublishedCount`, `WarmingCount` and `PendingCapacity` expose the transaction state. The scene BVH accepts only published slots. Hardware and global-distance-field integrations must apply the same visibility rule; simply testing `identity.w > 0.5` is sufficient for preparation, but would expose duplicate geometry in a live ray backend.

The ordinary unified sample also reports its own latest representation request in the UI and F2 ledger. `requestedRepresentation` distinguishes details, aggregate, no request and a request not yet evaluated; `requestEngineFrame` identifies that Update. `availableRepresentation` describes the currently bound, renderer-submittable authored set retained from publication. This exposes the case where detail pages are still binding, the Scene sees only the root, but the sample already wants details. An available aggregate can then be labeled as serving a detail request. Incomplete/mixed/invalid sets remain unknown, and an intentional withdrawal is not called missing coverage. These are sample CPU states, not pixel coverage or GPU completion; existing publication frame fields remain separate.

Pure commits tag old-removal/new-addition records with `ChangeKind.Representation`. A local-change consumer must preserve the target's prepared lighting while making surrounding transport reactive. Otherwise the removed aggregate bounds could hard-clear all freshly warmed detail patches at the instant of publication.

Material-only revisions keep unchanged geometry visible and invalidate lighting readiness. Transform, topology and unknown/manual edits remove stale geometry immediately, even if that creates a temporary coverage gap while replacement work waits for budget. Atomic publication never makes obsolete geometry correct. New groups have no previous representation to retain and remain unpublished until preparation completes.

Readiness means initialized data for the accepted revision/generation, not irradiance convergence. Targets that change every frame may not present a consistent ready snapshot before the next revision. Baked charts currently require readable, undeformed MeshRenderer sources; deformation requires rebaking and appropriate revision updates. Authored aggregate meshes are not automatically regenerated when individual detail meshes deform. Applications must update the aggregate or exclude such dynamic objects from that HLOD group. Missing async-readback support, persistent failures or insufficient preparation budgets do not trigger an unsafe timeout publication.

## Explicit additive-scene manifests

Create **Assets > Create > Hybrid Lumen GI > Scene Streaming Manifest**. Each entry provides a unique ID, an exact `Assets/.../*.unity` path, world bounds and load priority. Include these scenes in the application's Build Settings. Add `HybridLumenGIChunkStreamer` to a persistent bootstrap object, assign the manifest and observer, and configure load/unload distance, maximum owned resident scenes, concurrent operations and new operation attempts per frame.

Optional `additionalObservers` in the inspector, or `SetAdditionalObservers(params Transform[])`, add explicit viewpoints to the legacy observer/main-camera fallback. The setter copies the array; null/empty removes additions. The nearest viewpoint controls each chunk's distance demand, with one shared operation budget per frame. All viewpoints must leave the unload distance before demand is withdrawn; no live viewpoints leaves the state unadvanced. This does not authorize unloading or register cameras automatically. The separate asset-page representation also has its own explicit viewpoint collection.

The driver uses `SceneManager.LoadSceneAsync(..., LoadSceneMode.Additive)` and `UnloadSceneAsync`. Loads use distance hysteresis and reserve residency/concurrency capacity while in flight. Failed attempts also consume the per-frame start budget and receive a 60-step retry backoff. A load that becomes unwanted cannot be cancelled; it completes and then waits for safe unloading.

New load requests use author priority, nearest distance and ID. After 60 consecutive eligible scheduling steps, the longest-waiting loads take precedence, with the usual order breaking ties. A withdrawn request or a retry backoff starts a new wait. Safe unloads retain precedence, and each load still needs available residency and an operation slot. [Controlled scheduling result](../LocalComparison/Review/additive-load-fairness-222/result.md)

Before unloading an owned chunk, application orchestration must call `ReportUnloadSafe(id, generation, true)` after a replacement representation is published and no camera depends on the chunk. This gate defaults to false. The current generation is available in `ChunkStreamer.State.States`; an old generation cannot authorize a later load. A scene already loaded by another system is never adopted for automatic unloading. If an owned scene is externally replaced, its new scene handle is also treated as externally owned.

The IO driver does not silently unload scenes when disabled or destroyed. Native operations cannot be cancelled, so the application retains those scenes and must resume or transfer orchestration explicitly. The resident-scene limit covers scenes owned/loading through this driver, not unrelated application scenes or a measured byte budget.

Cross-scene HLOD membership is an application integration concern. Bind newly loaded detail proxies to a persistent authored aggregate through `SetHLODParent`; Unity cross-scene serialized references must not be assumed to establish those links. This module does not automatically register membership or infer cross-camera unload safety, generate aggregate meshes, load Addressables, or implement disk-level sparse SDF brick streaming.

## Offline verification

`Tests/Validate-HlodTransactions.ps1` compiles the actual scene/BVH/readiness source and checks readiness gates, stale reports, multi-frame warm-up, whole-group commits, cancellation, insufficient staging capacity, material-only retention, immediate stale-geometry removal, nested root/leaf grouping and readiness invalidation. A CPU sequence models `SetHLODParent` and member withdrawal with controlled readiness receipts.

`Tests/Validate-ChunkStreaming.ps1` compiles the actual IO policy against a fake asynchronous backend and checks operation/residency limits, hysteresis, unload authorization, uncancellable loads, generations, external ownership, scene-handle replacement, failure budgets and retry backoff. These checks do not execute Unity scene IO or GPU work. Engine integration, activation spikes, rendered transitions and cross-camera unloading remain runtime validation requirements.

`Tests/Validate-HlodReadback.ps1` exercises callback coordination with recorded requests, including variable/noncontiguous cards, required-chart coverage, stale layouts/source data, generation reuse and cache ping-pong. Callbacks use supplied CPU arrays; they do not establish native GPU completion. Use the unified `Tests/Validate-Offline.ps1` report and source hashes for the current candidate's individual outcomes. No Unity/GPU production acceptance is claimed.
