# Astra independent result review

Reviewed 2026-10-28 from existing source, reports and raw records. No Unity run, compiler, test suite, additional samples or analyzer rerun was performed. Only this requested review file was written.

No blocking omission was found. The package is ready for Pro review as a successful finite locator and an inconclusive optimization that was correctly withdrawn. It must not be presented as a retained performance improvement or a completed performance acceptance gate.

Both runs contain 240 frames and the same preselected 64 sources, 145–208. Independent reading confirmed 64 unique parent and 64 unique child completion records for each selected window. Raw spot checks at sources 145, 177 and 208 match the recorded parent association, distinct owners, generation/device/frequency and interval nesting; their completion lag is two frames. The frozen analyzer additionally enforces the full selected set, fixed workload and stable counters. Both native processes exited with code zero, without a watchdog termination or matched failure signature. Their final generic retirement reports have zero tracked owners, pending/unknown/failed items, material/arena/deformation bytes and jobs. The two out-of-window diagnostic pending items are recorded as canceled; cancellation is not proof that those queries completed. The ordinary UTP aggregate remains in the log and is not converted into either an attributed leak or a universal leak-free claim.

The comparison supports withdrawal. Gather median changes from 16.907376 to 16.879520 ms: a 0.027856 ms saving, about 0.165%. The candidate four-block median range is 1.138176 ms, so the predeclared benefit gate is false. Transport changes from 19.626784 to 19.610416 ms and FormalSum from 19.784896 to 19.770336 ms; neither establishes a meaningful improvement either. The last candidate block is slower, but this evidence does not identify register pressure, thermal behavior, driver compilation or another mechanism as its cause. The valid conclusion is that this one candidate did not establish sufficient benefit under the frozen rule, not that receiver reuse is universally ineffective or that a regression was proved.

The earlier helper and compiler results retain their bounded meanings: 60 saved footprint outputs match bitwise, and the inspected optimized DXC representation moves the intended receiver depth loads out of the loop. Neither result implies full-frame image equality, physical register behavior or a speedup on the physical GPU. The actual native comparison supplies no reason to retain the added live values and code.

I independently compared the two instrumentation manifests and build-input maps: diagnostic source wiring is identical, input path sets match, and Kernels is the only changed build input. The reported output-file counts are 284 and 283. That count difference alone is not evidence of a missing dependency or invalid comparison. The candidate source/patch and its newline mapping remain archived. Reading and hashing the locator manifest's 110 product sources confirmed that both the repository and Unity deployment now match that baseline exactly; the rollback is real, not merely a recorded intention.

This ends the planned locator/candidate package. Keep the finite Gather attribution and all rejected-candidate evidence; do not add samples, further hotspot subdivisions or a second reuse attempt to rescue the result. Production tail latency, total VRAM, broader dynamic quality and long-duration support remain open without blocking submission of this bounded evidence.

The highest-value next bounded question is one real material event on an existing Functional-scene renderer: change one material-slot `_BaseColor` property block while camera, geometry and lights remain fixed, then follow source observation, invalidation/recapture and actual GI consumption. `HybridLumenGIMaterialSource.cs` observes this property and its origin; `HybridLumenGISurfaceCache.cs:461–483` compares material snapshots and invalidates/rebuilds changed sources; `HybridLumenGIRendererFeature.cs:631` explicitly accounts for MPB edits without proxy revision changes. The existing RuntimeAuditProbe's material event also calls `Proxy.MarkDirty`, so copying that helper wholesale would bypass the automatic-detection question. Prefer the one property edit through the ordinary renderer API, with no manual cache/change injection, no simultaneous deformation and no dark-area investigation. Pro should set that finite event contract; this review does not authorize a new run or prescribe a broad material matrix.
