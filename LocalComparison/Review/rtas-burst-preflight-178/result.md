# 在准备 RTAS 前检查突发上限

Release155 在新构建超过 RTAS 突发上限时仍会准备三角属性并占用共享内存预留。录制阶段拒绝该构建后，活跃相机保留这些资源，另一个合格相机可能无法准入。修复在准备时应用录制阶段同一项三角和实例突发上限。[实际 Backend 与 Budget 对照](../../../Tests/StandaloneHardwareBackend/Program.cs.txt)

## 同额度对照

使用实际 `HybridLumenGIHardwareBackend` 和 `HybridLumenGIRtasBudget`。宿主记录 Unity 网格读取、属性分配和 RTAS 命令，提供受控的销毁回调。两个相机先后申请，较大相机有 7 个三角，突发上限为 6，随后的小相机有 1 个三角。共享内存余量为 123,456 B，足以单独准入小相机及宿主报告的构建大小。两份准备预留之和超过该余量。

| 观察 | Release155 | 修复版 |
| --- | --- | --- |
| 大相机的顶点读取 | 1 次 | 0 次 |
| 大相机的新增 RTAS 预留 | 67,904 B | 0 B |
| 大相机录制构建 | 拒绝 | 拒绝 |
| 大相机保持活跃时小相机录制 | 共享内存准入拒绝 | 录制一次构建 |

降低突发上限后，当前几何和位姿都未变的已建 RTAS 继续使用。移动对象后，修复版回退且未向旧 RTAS 写入新位姿。旧资源保留到受控完成，再恢复原额度后可构建当前位姿。普通等待额度积累与最老需求优先沿用原合同。

采用范围为 CPU 准入、命令录制与受控资源退休。真实 GPU 成本、驱动内存及整体 G4／G5 继续验收。
