# Additive 场景加载的等待公平

原第 5 节要求调度纳入等待年龄并防止请求长期得不到服务。可选 `HybridLumenGIChunkStreamer` 把主视点和附加视点交给同一个 `HybridLumenGIChunkStreaming.Step`，使用共享的驻留、并发和启动额度。本次复用现有 CPU 宿主，执行实际调度器源码，异步 I/O 完成由宿主控制。

三个场景的作者优先级相同。主视点始终在 B 的加载带内，附加视点在更近的 A 与 C 之间切换。已离场场景在取得当前代次的安全回执后卸载。驻留上限为 3，并发及每步启动上限均为 1。B 在整个对照中持续请求且有驻留余量。

| 同一输入 | 持续请求的 B | 共享额度与卸载 |
| --- | --- | --- |
| Release190 原调度器 | 64 步仍未启动。启动名额轮转给 A／C 的加载和安全卸载 | 每步至多启动 1 项，所有卸载走当前回执 |
| 本次修复 | 第 60 步启动，第 61 步读到完成并由驱动持有 | 同一额度、场景所有权和安全卸载门 |

新请求按作者优先级、最近距离和 ID 排序。持续合格的请求达到 60 个调度步后，按等待时长优先排序。同龄仍沿用作者顺序，因此久等请求可以越过更新的高优先级请求。请求撤回、进入失败退避或实际发起时重置等待。60 步决定排序，实际启动还取决于安全卸载、驻留和操作名额。

本次实际前后对照覆盖同优先级的场景加载推进、既有共享额度及安全回执。历史单视点对照入口仍可运行。`SceneManager` 原生 I/O、实际等待时间、其他流式路径和生产预算分别验收。[实际源码回归](../../../Tests/StandaloneBvh/StreamingProgram.cs.txt) · [原调度目标](../../../Documentation/ProductionPlan.md#5-streaming-与预算)
