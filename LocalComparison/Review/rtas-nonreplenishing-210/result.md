# Release182 使用未补充的 RTAS 余额

RTAS 构建次数和突发上限允许时，三角和实例积分可以跨帧累积。下一帧停止补充某一项后，已有余额仍可支付合格请求。旧版仍让超过该项余额的旧请求占据队首，后续能支付的请求随之等待。Release182 在准备、排队和录制时使用同一项准入。选取本帧队首时跳过当前不可执行的请求，持有者下次准备并遭拒时撤回请求。其他相机同帧收紧额度期间，等待票龄可延续到下一帧。原生资源按各自完成条件退休。[共享预算](../../../Runtime/HybridLumenGIRtasBudget.cs) · [实际 Backend](../../../Runtime/HybridLumenGIHardwareBackend.cs)

旧新版用同一实际 Backend／RtasBudget 宿主。正补充帧留下 4 个三角积分和一个需要 6 的旧请求。下一帧把三角补充改为 0，保留正构建次数、足够的突发上限与实例额度。需要 3 个三角积分的新相机在旧相机重新准备前提交。

| 观察 | Release181 | Release182 |
| --- | --- | --- |
| 新帧的旧请求是否挡住小相机 | 是 | 否 |
| 小相机构建、扣费和余额 | 未录制，扣 0，余 4 | 录制一次，扣 3，余 1 |
| 新冷请求的顶点读取／RTAS 估算预留 | 1 次／67,712 B | 0 次／0 B |
| 已准备的无效计划 | 继续持有预留 | 转入退休，在受控完成前保持计账 |

修复后，已建且仍匹配的 RTAS 在余额不足以重新构建时仍可提交。恢复补充后，旧相机可以重新构建。同帧实例积分收紧到零的计划按原完成门退休。初版剪除等待票会抹掉下一帧的 HLOD 顺序，经独立复核后改为按当前额度选队首。最终对照包含帧末收紧构建次数、下一帧 HLOD 保有等待顺序和明确撤回，以及正补充积累、突发上限和零构建次数。Astra Max 采用范围为 CPU 准入、命令录制及受控退休。实际 DXR 画面、驱动分配和生产预算按各自条件验收。[定向回归](../../../Tests/StandaloneHardwareBackend/Program.cs.txt)
